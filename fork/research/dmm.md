# Debrid Media Manager + decypharr — recommendation (2026-09-26)

**Keep DMM integration in Go in the decypharr fork; keep dler Rust and hoster-link/RD-only.** DMM's useful role here is discovering/sharing torrent infohashes and supplying a cache hint; decypharr already owns torrent providers, TorBox cache checks, provider synchronization, and the mount. A Go-native import avoids a second torrent stack and is easiest to carry upstream. Build a direct DMM hashlist importer first; treat DMM's cache database endpoint as an optional, rate-limited hint—not as an authoritative or supported public API. DMM is AGPL-3.0-only; avoid copying DMM application code into decypharr without reviewing license implications. [DMM `package.json`](https://github.com/debridmediamanager/debrid-media-manager/blob/main/package.json#L1-L6); [DMM README](https://github.com/debridmediamanager/debrid-media-manager/blob/main/README.md#license)

## Ranked integration options

| Rank | Option | Value / effort | What it does |
|---|---|---|---|
| 1 | **Import hashlist into a named decypharr list** | High / Low–medium | Paste DMM share URL or hashlist into decypharr UI, parse title + torrent entries, deduplicate by infohash, then add to selected TorBox/RD provider. Prefer TorBox's existing cache-check+`add_only_if_cached` path; surface uncached/failed entries instead of silently adding unwanted downloads. DMM shares `{title, torrents:[{filename,hash,bytes}]}`; URL payload is JSON compressed using `lz-string`'s `compressToEncodedURIComponent`. [DMM `hashList.ts`](https://github.com/debridmediamanager/debrid-media-manager/blob/main/src/utils/hashList.ts#L20-L55); [decypharr TorBox client](https://github.com/sirrobot01/decypharr/blob/main/pkg/debrid/providers/torbox/torbox.go#L198-L263) |
| 2 | **Use DMM cache database availability as an RD cache hint** | High / Medium–high | Query DMM's hash lookup in batches (currently up to 100), then submit positive candidates to RD only; handle unknown/missing/stale as “not confirmed,” not “uncached.” This fills the gap from RD disabling `/torrents/instantAvailability` in Nov. 2024. Important caveat: DMM's `/api/availability/check2` requires `dmmProblemKey` plus `solution` and is app-internal, not a documented anonymous public API; validate its stability/terms before coupling production behavior to it. [DMM `check2.ts`](https://github.com/debridmediamanager/debrid-media-manager/blob/main/src/pages/api/availability/check2.ts#L9-L57); [DMM availability client](https://github.com/debridmediamanager/debrid-media-manager/blob/main/src/utils/availability.ts#L84-L125); [al's verified brief, 2026-09-26](../briefs/debrid-downloader.md#real-debrid-api-facts) |
| 3 | **Sync existing DMM-added provider items into decypharr library/mount** | Medium–high / Medium | Reconcile provider torrent lists into decypharr's existing torrent model, preserving provider identity, files, and hash dedup behavior. Existing open PR #275 explicitly proposes adopting completed provider torrents including those added via DMM; issue #287 documents the resulting duplicate-hash/provider mount behavior. Review/coordinate with those upstream changes rather than implementing a conflicting second sync path. [PR #275](https://github.com/sirrobot01/decypharr/pull/275); [issue #287](https://github.com/sirrobot01/decypharr/issues/287) |
| 4 | **Recurring DMM library ↔ decypharr synchronization** | Medium / High | Keep additions/deletions aligned, with explicit ownership and deletion policy. DMM README says it does not monitor continuously; it reads library data when the Library page opens and caches it in browser local storage. DMM hashlist sharing is a snapshot, so it is not itself a sync protocol. Build only after one-way import and provider sync semantics are established. [DMM README FAQ](https://github.com/debridmediamanager/debrid-media-manager/blob/main/README.md#faq); [DMM `hashList.ts`](https://github.com/debridmediamanager/debrid-media-manager/blob/main/src/utils/hashList.ts#L40-L55) |

### What “optimized” should mean

- **Batch and deduplicate before network calls.** TorBox's decypharr client already submits up to 100 hashes per `/api/torrents/checkcached` call and sends `add_only_if_cached=true` when uncached downloads are disabled. Preserve this batch size / provider behavior; avoid one API request per item. [decypharr `torbox.go`](https://github.com/sirrobot01/decypharr/blob/main/pkg/debrid/providers/torbox/torbox.go#L198-L245)
- **Cache availability results with a timestamp/source.** Reuse fresh positive/negative lookups for repeated hashlists; expire them and retain unknown/stale states so a cached-but-now-evicted torrent is not treated as guaranteed. This is a recommendation, not existing decypharr behavior.
- **Protect RD's quota.** The project brief verifies RD's limit as 250 requests/minute, with rejected 429s also counting. Apply a shared client-side limiter to any RD torrent import/add/unrestrict activity and batch where endpoint semantics allow; do not use a DMM cache result to bypass provider error reporting. [al brief, § Real-Debrid API facts](/home/al/Code/al/infrastructure/briefs/debrid-downloader.md#real-debrid-api-facts)
- **DMM-specific warning:** DMM cache lookup code groups requests by 100 and throttles its own calls; its exposed implementation routes require app problem-token authentication. This is evidence of an app endpoint, not evidence of a supported third-party API or an SLA. [DMM `instantChecks.ts`](https://github.com/debridmediamanager/debrid-media-manager/blob/main/src/utils/instantChecks.ts#L94-L116); [DMM `check2.ts`](https://github.com/debridmediamanager/debrid-media-manager/blob/main/src/pages/api/availability/check2.ts#L15-L57)

The data fields are enough for decypharr's torrent path: hash, display filename, byte size. DMM code excludes rows without a valid torrent infohash from sharing (e.g. some web-download rows). [DMM `hashList.ts`](https://github.com/debridmediamanager/debrid-media-manager/blob/main/src/utils/hashList.ts#L8-L18) |

## How al's workflow fits

1. In DMM, curate a collection and share/export a hashlist. It gives torrent name, infohash, and size, not the debrid account's private torrent ID or authenticated playable URL. [DMM `hashList.ts`](https://github.com/debridmediamanager/debrid-media-manager/blob/main/src/utils/hashList.ts#L40-L53)
2. Paste the DMM URL/hashlist in decypharr. Decypharr parses/deduplicates hashes, checks availability using the chosen provider (TorBox's existing batch cache check; RD could use DMM indexed availability as an optional prefilter), then creates provider torrent entries.
3. decypharr's provider sync/mount exposes the selected provider's files, and its common `__all__` view can make them visible to the media consumer. al's desired path `/mnt/decypharr` is a mount-path setting, not a DMM behavior; decypharr's mount config has `mount_path`. [decypharr `mount.go`](https://github.com/sirrobot01/decypharr/blob/main/internal/config/mount.go#L5-L20); [issue #287](https://github.com/sirrobot01/decypharr/issues/287)
4. For an automatic workflow, decypharr would have to periodically enumerate provider libraries and reconcile them; DMM itself says library monitoring happens on opening its Library page and uses browser local storage. A hashlist is therefore a manually refreshable snapshot unless a separate API/sync integration is deliberately added. [DMM README](https://github.com/debridmediamanager/debrid-media-manager/blob/main/README.md#faq)

This is distinct from al's new **dler** daemon: dler's assigned scope is hoster links → Real-Debrid unrestrict → download/stream; torrent hashes and mounts remain decypharr's domain. [al brief, § Torrents](/home/al/Code/al/infrastructure/briefs/debrid-downloader.md#real-debrid-api-facts)

## Go vs Rust, and existing clients

**Recommendation: Go in decypharr, no Rust port.** Decypharr is a Go application with Go provider interfaces and existing TorBox/RD provider integrations; the proposed import naturally calls those interfaces and is easier to merge upstream as a focused PR. Existing open PR #275 demonstrates upstream interest in DMM-originated/existing provider torrents. A Rust rewrite would duplicate existing provider, account, queue, file-layout, and mount logic, increase maintenance surface, and be harder to upstream. dler being Rust is not a reason to port torrent workflows: its brief explicitly keeps torrents/magnets/hashlists with decypharr. [decypharr `go.mod`](https://github.com/sirrobot01/decypharr/blob/main/go.mod); [PR #275](https://github.com/sirrobot01/decypharr/pull/275); [project brief](../briefs/debrid-downloader.md)

A GitHub repository search on 2026-09-26 for `debridmediamanager`/“Debrid Media Manager” in Go and Rust found no dedicated Go or Rust DMM client. The DMM upstream itself is TypeScript. Search results for similarly named “DMM” Go clients referred to the unrelated Japanese Digital Media Market API, not Debrid Media Manager. [DMM `package.json`](https://github.com/debridmediamanager/debrid-media-manager/blob/main/package.json#L1-L5); [GitHub repository search](https://github.com/search?q=debridmediamanager+language%3AGo&type=repositories); [GitHub repository search](https://github.com/search?q=debridmediamanager+language%3ARust&type=repositories)
